# How Sillage is built

This page is for those who read or change the engine itself. To make games, start with the [README](../README.md), the [tutorial](TUTORIAL.md) and the [guide](GUIDE.md).

## Principles

- **Kotlin and nothing else.** No third-party library in the engine or the games (the toolchain brings its own test runner). On the desktop the engine talks to the system's C libraries (on Linux and the BSDs `libvulkan`, `libwayland-client`, `libxcb`, `libasound`, `libc`; `libxkbcommon` for typed text, optional: without it a US table; `libEGL`, `libGLESv2` and `libwayland-egl` for OpenGL ES when Vulkan is not there; on Windows `vulkan-1`, `user32`, `kernel32`, `winmm`) through the JDK's Foreign Function & Memory API (`java.lang.foreign`); in a page it calls the browser through `@JsFun`, on Android the platform's own classes. Within the JDK it uses only the runtime basics: atomics, thread parking, FFM. Assets come from files or from code: models are glTF files made by `tools/create_assets.py`, and sounds are synthesised.
- **Built with the Kotlin Toolchain** (`./kotlin`), on JDK 25, which the toolchain provides. No Gradle. The `./sillage` script (new, run, dev, test, qa, package, doctor) calls the toolchain only to compile, and only when a file changed, then starts the JVM itself on the compiled classes: a run with nothing to build takes under a second instead of nine.
- **Deterministic physics.** The same inputs give the same bits, whatever the number of threads. Fingerprint tests guard this.
- **No garbage in hot loops.** The physics step, collision tests, queries, the joints' common passes, the mixer, posing animated models and frame recording work on arrays and plain numbers. The public types (`Vec3`, `Quat`, `Mat4`, `Color`, `Body`…) are immutable values marked `@ValueCandidate`, ready to become value classes with Valhalla. Where a hot path used to chain them (`a.rotate(v) - b`, `m1 * m2`), it is written out on floats with the very operations of those functions, in their order, so that the results stay the same to the bit; only the values a game can see (a node's new position, a part's `pose` when asked for) are made. A scene still makes a few kilobytes a frame, mostly for the values that change every frame by nature (the hour's colours, the camera, ray hits) and in the hinge's own rows and the character's substeps.
- **A public API in English**, documented where it is declared (KDoc) and in `docs/`. Many test names and quality-check messages are in French, the authors' language.

## A frame

`game()` builds the scene, opens the window (on Windows a Win32 one; elsewhere Wayland if `WAYLAND_DISPLAY` is set, else X11; `SILLAGE_PLATFORM=wayland|x11` forces one) and the renderer, then loops:

1. **Window**: events, resize. Without focus the loop waits.
2. **Waiting for the screen** (`VulkanRenderer.attendre`): until the last frame is on screen (`VK_KHR_present_wait`, when the driver offers it), then until this frame's fence and a swapchain image are free. Then the window's events are read again, mouse movement and wheel included: whatever came during the wait acts on the very next picture.
3. **Input**: `input.poll()` reads the keys from `input.source` (the window by default) and works out which went down this frame. A key that went down and up between two frames still counts as down for one frame (the windows keep it until `clearPresses`).
4. **Scene update** (`Scene.update`): key actions, the camera's switch key, timers, the scene's `onUpdate` blocks, then each node's blocks; animators advance; kinematic bodies and colliders that follow animated parts get their target velocities; **the physics steps** with the frame time, clamped to 1/240–1/30 s; dynamic nodes take their bodies' places; players update their characters (after the step, so they stand where the platforms are); blob shadows follow; the hour moves on (`Lighting.advance`); the scene's own effects (dust where players land, splashes where things fall into water), then the emitters and the particles; scene sounds update.
5. **Camera**: the view matrix, after the players moved.
6. **Drawing** (`VulkanRenderer.dessiner`): see below, with `Scene.frameExtras` (the 128 lamps nearest the eye at most, dimmed by day if they only light at night, wavering, each with its `PointLight.id`; the particles in flat arrays, the farthest from the eye first). The HUD's mesh is rebuilt only if what it shows changed.

Without a window (`--headless`), the same loop draws into an off-screen image with a fixed 1/60 s step, mixes the sound frame by frame and can save the last frame as a PNG. `Scene.step` runs steps 3–5 without any renderer, for tests.

## Rendering

- **Vulkan through FFM** (`vk/`). `Vulkan.kt` loads `libvulkan.so.1` (`vulkan-1.dll` on Windows) and keeps one `static final` method handle per call signature, which the JIT inlines; the function's address is an argument. `Struct.kt` describes C structs (alignment, nested fields, arrays) and provides `NativeStack`, a native scratch stack reused every frame. `Structs.kt` and `Constants.kt` were written from the Vulkan registry and checked field by field against LWJGL's layouts before LWJGL was removed.
- **Two frames in flight.** Each has its command buffer, fence, semaphores, a persistently mapped instance buffer and HUD buffer. A frame first waits for its fence, so the CPU prepares frame n+1 while the GPU draws frame n.
- **Latency.** In FIFO mode the swapchain (4 images on Mesa under Wayland) let up to three frames wait for the screen: a key read at the start of the loop reached it about 100 ms later at 60 Hz (measured in a headless KWin). Now each present carries a number (`VkPresentIdKHR`) and the next frame waits for it to be shown (`vkWaitForPresentKHR`, at most 0.1 s, as a hidden window may never be shown) before the keys are read: 16.6 ms from the keys to the screen at 60 Hz, still 60 frames per second. The frame then has one refresh for its CPU and GPU work. Without the extension (or with `SILLAGE_PRESENT_WAIT=0`), the swapchain keeps `minImageCount` images, one fewer frame queued. `SILLAGE_LATENCE=1` prints once a second the keys-to-screen time and where a frame waits.
- **Culling** (`RenderBatches.gather`, the same code for both renderers): each copy's bounding sphere (the mesh's, `Mesh.sphere`, placed by the node; a node that has not moved keeps it, its position, rotation and mesh being immutable values compared by identity) is tested against the six planes of view × projection (Gribb–Hartmann, depth 0 to 1), the haze's end and the node's draw distance; a second list holds what stands in the shadow square (its sides along light.glsl's axes), drawn alone into the shadow map. Batches are found through the mesh (`Mesh.batches`, valid for the renderer's current `token`), not by hashing. `--no-cull` draws everything; qa `mondes` checks that the picture is the same.
- **Still cells** (`StillCells.kt`), so that a large world is not visited node by node every frame. A node whose placement and looks have not changed for 30 frames joins a cell of a grid over the ground (x, z; the side chosen for about 16 nodes a cell, chosen again when the still nodes have grown fourfold): visible, not the sky, a blob shadow, a player or an animated model, drawing meshes that do not change, and not larger than four cells (the ground, a sea). Node's setters (`position`, `rotation`, `scale`, `mesh`, `visible`, `parts`, `drawDistance`, `lod`, `animator`) compare the new value with the old one and, on a change, take the node out of its cell at once (`Node.stir`); a body at rest leaves its node untouched, so a sleeping pile joins too. Each cell keeps the box holding its nodes' spheres (of every level of detail) and their longest draw distance. A frame first tests the cells: a cell is left out whole when its box is past the haze and the draw distances, or outside the frustum and every shadow square drawn this frame, with a margin of a millimetre plus 2·10⁻⁵ of the coordinates, so that it is left out only if each of its nodes surely would be. The nodes kept (those outside the cells, and those of the cells not left out) are then visited in the draw list's order, through one bit per node, and each is tested exactly as before: the batches, their order, their rows to the bit and the counts are what visiting every node gives (`CullTest.lesCellulesDonnentLesMemesLots`, 240 frames of changes, against the node-by-node path). When the cells left out hold fewer than an eighth of the nodes, every node is visited, which costs less than choosing. A cell holds its nodes' places in the list, not the nodes: with references to the nodes, the collector copied them in the cells' order, and walking the list in its own order then read memory out of order (10,000 crates in sight drawn 20 % slower); `Scene.remove` keeps the places right. Forest of 40,000 blocks (qa `mondes`), CPU per frame without the capture: 1.33 → 0.70 ms. The frame's preparation stays on the render thread: the physics' pool (`Workers`) is internal to `core`, out of the engine's reach without new public API.
- **Instancing.** Nodes are grouped by `Mesh` (by identity), in `RenderBatches.gather`, kept apart from the rest of `dessiner`: a smaller method that C2 compiles on its own (inside the large one, the loop ran up to six times slower, depending on the run). Each group's model matrices go into the instance buffer as three `vec4` rows (attributes 3–5), and the group is drawn in one call. Scene primitives with the same parameters share one `Mesh`, so a thousand identical crates cost one draw. A mesh goes to the GPU the first time it is seen.
- **The frame's light in a uniform block** (`frame.glsl`, one per frame in flight, mapped for good): the main light (the sun, or the moon at night), its colour, the shade, ambient, sky gradient, haze, the sun and moon in the sky, the wind, the camera's axes (for particles), the light grid's parameters and the lamps (128 positions and colours, each colour's `w` the lamp's shadow cube, 0 for none). Everything in `Lighting` can therefore change from one frame to the next without touching the pipelines.
- **Many lamps** (`RenderBatches.lights`, common to both renderers). Up to 16 lamps, they all go to the shaders and every point loops over all of them, as before. Past 16, the lamps whose reach (two and a half radii, for their glitter on water) misses the frustum or lies beyond the haze are left out, and a light grid is built on the CPU: 16 × 10 tiles of the picture and 16 slices of distance from the eye (the first ends at 1.5 m, the others double the distance in equal steps up to the farthest lamp's reach), up to 15 lamps per cluster, the nearest first; a lamp goes into every cluster that the box around its sphere projects onto and its distance range crosses. The grid is an RGBA8 image of 640 × 16 texels (four per cluster: the count, then the lamps' places in the frame's list), sent only on frames that use it and read by `texelFetch` (`pointLights` in `shading.glsl`) in the variants of the scene's fragment shaders that know of it (`toon_grid.frag`, `water_grid.frag`, `particle_grid.frag`: the same bodies, `toon.glsl`…, with `LIGHT_GRID`), bound only on frames that have a grid, so that the others keep their registers (128 instead of 160 on the Arc, by `INTEL_DEBUG=fs`). The water's glitter takes the first 16 lamps of the list.
- **Lamps' shadows** (`RenderBatches.lights`, `scheduleFaces`; `lamp_shadow.vert`). The lamps that matter most get a cube of shadows: importance = brightness × (radius / distance to the eye)², the distance at least half the radius, ×1.3 for a lamp that already holds a cube; at least 0.5 and a tenth of the first; at most `RenderQuality.lampShadows` (4, 2, 1) with faces of `lampTexels` (512, 256, 256). A cube is six layers of a D16 array image, one per face of 90° and three texels (their projection's scale `s = 1 − 6/size`, so that the four filtered lookups near an edge stay on the face), with depth from the near plane (a tenth of the radius, 0.15 to 0.8 m: what stands that close casts nothing) to the radius. `RenderBatches.gather` tests each copy's sphere against each cube face's pyramid, and sorts the casters into still ones (a node or part whose place, pose and mesh have not changed for 8 frames) and moving ones. Each face keeps a cache (a second array image) of what stands still, drawn again only when the hash of the lamp's place and of its still casters' rows changes, within a budget of 30 000 triangles per lamp slot per frame (a face that does not fit waits; the first always fits); the face the shaders read is copied from the cache (`vkCmdCopyImage`, `glBlitFramebuffer`) with the moving casters drawn over it, when anything moves in it. A lamp that moves draws its six faces straight into the faces read, or casts no shadow that frame (and gets no cube for a second) if they do not fit the budget. Swaying is left out of lamps' shadows (they would otherwise be drawn every frame). In `shading.glsl`, `lampLight` picks the face from the direction's largest axis, offsets the point along its normal by about a texel, compares four filtered lookups; half of a lamp's light stays in its shadow. Particles do not read lamps' shadows.
- **Blended surfaces.** A mesh whose `Mesh.surface` gives some triangles an opacity (glTF `BLEND`) is split once (`Mesh.blendSplit`): the opaque part is drawn with the other copies, the blended part one copy at a time after the blob shadows, among the particles: the blended copies are sorted from the farthest to the nearest (by their own part's centre), and the particles (already sorted) are drawn in runs between them (`firstInstance` in Vulkan, the attribute offset in OpenGL ES). `toon.frag` writes a blended surface premultiplied by its opacity, and its blending keeps the destination's alpha (the distance, for the ink). Shadows still come from the whole mesh, cut out at half opacity. A frame with blended copies asks the next one's particles to be sorted even if they all glow (`FrameExtras.sortParticles`).
- **Passes.** (1) The shadow maps: a 2048 × 2048 depth image (D16) of three layers, one per cascade, each drawn from the main light by `shadow.vert` alone (a second pipeline adds `shadow.frag` for the meshes cut out by an image's alpha, so that their shadow has the shape drawn and the others pay nothing) through an orthographic box around the camera's focus (`light.glsl`; half sides from `Lighting.cascadeHalf`, the depth range growing with the square), its centre snapped to the map's texels so that shadow edges stay still, with a slope-scaled depth bias. The second layer is drawn every two frames and the third every four; a layer not drawn again keeps the square it was drawn for, and the frame block (`cascade[3]`) gives the shaders each layer's real square. `shading.glsl` picks the finest square holding the point and blends into the next near its border. Then the lamps' cube faces that changed (see Lamps' shadows). (2) The scene in linear light, RGBA 16-bit float with 4× MSAA when available, resolved into a single-sample image; its alpha holds the distance to the eye. Opaque nodes (`toon.vert`/`toon.frag`), water (`water.frag`), the sky dome (`sky.frag`, gradient, sun, moon, stars), blob shadows (`ombre.frag`) and particles (`particle.vert/.frag`, one square per instance facing the camera; glowing ones add, the others are blended premultiplied) with the blended surfaces among them, farthest first, the blended ones leaving the distance as it was. (3) The halo: the parts brighter than white at half size (`bright.frag`, soft knee), down four more levels (`down.frag`), then up again adding each level (`up.frag`). (4) The finished picture (`composite.frag`) into an RGBA 8-bit image: ink where the distance jumps between neighbours, the halo, a soft shoulder above white, saturation, vignette, sRGB with a little dither; then the HUD over it (`hud.frag`, blended by each element's opacity). The picture is blitted to the swapchain, or read back for a capture and written by the engine's PNG writer (`io/PngWriter.kt`; `PngWriterTest` keeps fingerprints of its files, so that a faster encoder still writes the same bytes and captures still compare byte for byte).
- **Toon shading** (`shading.glsl`, shared by the fragment shaders): a soft two-tone light (sun colour and shade colour), sky and ground ambient, a rim light, haze towards the sky behind, the lamps (windowed inverse-square falloff, soft toon steps) and the cast shadows: nine filtered lookups of the map through a comparison sampler, the point taken a little off the surface along its normal so that a face never shadows itself, fading out at the map's border.
- **Material maps.** A model's mesh may also carry `Mesh.surface`, 8 floats per vertex (binding 3, locations 9 and 10; the zeros for the others): the tangent and its handedness, the normal map's layer and strength, the emission map's layer, and the opacity of a blended material. `MaterialMaps.kt` reads them from the glTF materials and makes the tangents a file lacks (each triangle's dP/du summed per vertex, made square to the normal, handedness from dP/dv); `Model` turns them with their nodes (and their handedness with a mirroring). `toon.frag` squares the tangent to the interpolated normal again (a skinned part's tangents are not deformed), bends the normal by the map (tangent space, +Y up the image, as glTF), and tints the vertex's own light by the emission map.
- **Per-vertex effects.** A mesh may carry 8 more floats per vertex (`Mesh.effects`, vertex binding 2; a zero buffer for the others): its own light (negative: only at night), how far it sways (moved in `swayed()`, in the vertex and shadow shaders alike, so shadows sway too), its texture, tile, strength and mapping. `Node.sway`, `glow` and `texture` write them, for the triangles of the materials named (`Mesh.materials`, kept when a model is flattened); a node then gets its own copy of the mesh, except textures laid by material name or on a whole shared mesh, which are cached so that copies stay one draw.
- **Image textures and skins** (`Glb.kt`, `Animation.kt`, `io/Png.kt`, `io/Jpeg.kt`). Images are decoded by the engine (inflate, PNG filters and interlacing; JPEG Huffman, progressive refinement, IDCT, chroma upsampling), cached by their encoded bytes so that a model loaded again reuses its textures (a scene that restarts would otherwise add layers to the texture array: 2.8 MB per scene, found by the leak check), scaled to a power-of-two square and stored in the same array as the detail textures; their texture coordinates and alpha cut-out go in the per-vertex effects (mapping 2). A skinned part gets its own copy of its mesh (`Mesh.dynamicCopy`); after each pose the animator writes its vertices (joint pose × inverse bind matrix, weighted) and bumps `Mesh.version`, and the renderer keeps one vertex buffer per frame in flight for it, sent again when the version moved. The animator keeps every node's pose as 16 floats (column first, as `Mat4` names its coefficients), worked out in place by `trsInto` and `timesInto` (the operations of `Mat4.trs` and `Mat4.times`); each part gets its 16 coefficients (`Part.m`), which the renderer reads as they are; `Part.pose` and `Animator.nodePose` make a `Mat4` only when asked for.
- **Detail textures** (`Texture.kt`, `texture.glsl`). The ready-made textures are painted by Kotlin code (value noise, cells, strokes and dabs, all wrapping around), on the common pool, as soon as they are made; their mean is brought to neutral grey and every smaller level is computed on the CPU. The renderer keeps one array image, a layer per texture (as large as the largest), sent through a staging buffer when new textures appear; until all are painted, the window shows the others neutral for a few frames (without a window, and before a capture, it waits, so that frames are the same from run to run). The fragment shader reads them in the object's own space: from the three axes blended by the normal (`textureGrad` with derivatives taken outside the branches), or along the face, its true normal from screen derivatives, rows level and climbing the slope.
- **Water**: `Water.kt` lays a grid over the shores, finds the land by rays from above (ground at most 0.9 m above the water counts; a pier's deck does not), computes each vertex's distance to the nearest shore (8SSEDT, then one smoothing pass) and stores it in the vertex colour's red channel. The green channel holds how near (1 at it, 0 at 1.5 m and beyond, so that the field fades towards "none" between two vertices) is where a steep solid thing cuts the water: the segments where static meshes' triangles steeper than about 45° cross the water level, and static bodies' outlines found by a sphere test at each nearby vertex; the blue channel how open the water is in front of such a wall (the longest run of water in eight directions, 6 m and less: 0, 20 m and beyond: 1), so that a basin stays calm. `water.frag` draws the lagoon, the foam, the surf and the crests from the shore distance, the world position and the time, and the ring and lace of foam at the foot of walls from the second distance, times the openness (0 on both when there is no wall: the beaches are drawn as before).
- **Push constants**: 128 bytes (the minimum every device guarantees): view × projection, eye and time, the shadow map's centre and half side, the water's two colours. The scene's descriptor set holds the shadow map, the frame's uniform block and the texture array; the picture's passes have their own sets, two images each.
- **Debug lines** (`Debug.fill`, `lines.vert`, `lines.frag`, `lines_xray.frag`): segments of two vertices (position, colour, opacity) written after the particles in the frame's instance buffer, drawn at the end of the scene pass twice: first without the depth test and faint (what the scenery hides), then with it. Both pipelines write red, green and blue only, so the alpha (the distance to the eye) and thus the ink lines stay as they were. Nothing is drawn, and nothing costs, while F5 is off.
- **GPU time** from timestamp queries, when the device supports them: the whole frame, and the shadow maps' part of it (the sun's cascades and the lamps' cubes; printed with `SILLAGE_LAMPES=1`).
- **What the card can do is asked, not assumed.** The depth format is the first the device accepts among 32-bit float, 24 bits and 16 bits; the 16-bit float pictures and their sample count are checked, and a missing one is said in words rather than left to the driver. `RenderQuality` (`RenderData.kt`) sets the shadow maps' side and the anti-aliasing: `high` (2048, 4 samples), `medium` (1024, 4), `low` (1024, 1), from `--quality`, `sillage.quality` or `SILLAGE_QUALITY`, else by the card's name (a Raspberry Pi's V3D gets `medium`). The run's first line (`SILLAGE_VULKAN_OK …`) says what was chosen.
- **Two looks from one shader.** `Lighting.softness` blends, in `shading.glsl`, the two drawn steps of the toon light into a smooth wrap with more ambient in the shade and a faint sheen; a model's `COLOR_0` multiplies its material colour vertex by vertex.

## The second renderer: OpenGL ES 3.0 and WebGL 2

`gl/GlRenderer.kt` draws the same frame as the Vulkan renderer, pass for pass, in common Kotlin, through the `Gl` interface (`gl/Gl.kt`: the part of OpenGL ES 3.0 that WebGL 2 also has, objects as numbers). A page implements `Gl` over its canvas, a phone over its surface; on the desktop `platform/EglGl.kt` implements it over EGL and `libGLESv2` through FFM, without a window (Mesa's surfaceless platform, else a pbuffer: `./sillage run demo --headless --renderer gl --capture out.png` compares its pictures with Vulkan's) or in the game's window, when Vulkan is not there (below).

- **One set of shaders.** `tools/shaders_gl.py` (Python's own library only) turns `engine/resources/shaders/*.vert|.frag` into `gl/GlShaders.kt`, GLSL ES 3.00 in Kotlin strings: `#version 300 es` and the precisions, `#include` pasted in, comments dropped; push constants become a std140 uniform block with the same name and members (`Push`, `Post`), blocks and samplers lose their set and binding (the renderer ties them by name: `uniformBlockBinding`, `uniform1i`); what a vertex shader hands to a fragment shader is named after its location (`v0`, `v1`…), since Vulkan matches them by location and OpenGL ES 3.00 by name; `gl_VertexIndex` becomes `gl_VertexID`. The sources needed no change, and the SPIR-V files are the same as before. `GlShadersTest` checks that the committed file is what the tool gives; after changing a shader, run `tools/shaders.sh` and `tools/shaders_gl.py`.
- **Clip space stays Vulkan's.** The camera matrix is the same (y down, depth 0 to 1); each generated vertex shader ends with `gl_Position.z = 2.0 * gl_Position.z - gl_Position.w` (OpenGL's depth runs from −1 to 1, so the depth written is the same 0 to 1), and nothing is flipped in the shaders. Every image is therefore drawn with its top row first in memory, exactly as Vulkan's: texture coordinates, `gl_FragCoord`, screen derivatives and the HUD's positions mean the same in both. The finished picture is turned the right way up once, by the `blitFramebuffer` that copies it to the screen (`GlRenderer.present`); a capture reads it as it is (its first row is the top one).
- **The same decisions.** `RenderBatches` (common code, used by both renderers) chooses the shadow squares drawn again this frame, culls, groups the copies by mesh and writes the frame's uniform block.
- **What differs under the same picture.** Uniform buffers bound by name stand for descriptor sets and push constants (four binding points: the frame, `Push`, `Post`, the HUD's). WebGL 2 has no base instance: each mesh has a vertex array, and a draw sets the three instance-row attributes at the batch's byte offset in the frame's instance buffer. A mesh without per-vertex effects reads zeros from constant attributes (`vertexAttrib4f`) instead of a zero buffer. Textures are immutable (`texStorage`); the scene is drawn into multisampled renderbuffers (RGBA16F and 32-bit float depth, 4 samples) and resolved by a blit into the texture the later passes read; the shadow maps are a `DEPTH_COMPONENT16` texture array read through a comparison, drawn with `polygonOffset(2, 1.5)` (Vulkan's slope-scaled bias) by `shadow.vert` and an empty fragment shader. The picture is written as sRGB by `composite.frag` itself into an RGBA8 image, as in Vulkan. The lamps' cubes are two more `DEPTH_COMPONENT16` arrays (the caches and the faces read, a blit between them), the light grid an RGBA8 texture sent by `texSubImage2D`; texture units 2 and 3 hold them. The renderer makes the shadow maps itself the first time a scene turns shadows on. It needs floating-point render targets (`Gl.floatTargets`: `EXT_color_buffer_float` or `_half_float`) and says so clearly otherwise.
- **On the desktop, in a window** (`GlDrawing` with `EglWindow`), when Vulkan cannot start or with `--renderer gl`. Under Wayland, `libwayland-egl` makes a `wl_egl_window` of the window's own `wl_surface`, and EGL's Wayland platform draws into it; the swap does not wait (interval 0): before each swap the window asks the compositor for a frame callback (`wl_surface.frame`, on the window's own queue), and the next frame waits for it, at most 0.1 s, as Vulkan's present wait does (a hidden window is never called back, and must not stop the game). Under X11, EGL's XCB platform takes the window's own connection (else EGL's X11 platform opens its own on the same server), with a configuration of the window's visual, and the swap waits for the screen (interval 1). The configuration has no alpha (the compositor would see through the window) and no multisampling (OpenGL ES 3.0 refuses a blit into a multisampled screen): the scene keeps its own 4 samples in renderbuffers. A resize gives `wl_egl_window_resize` the new size and the renderer makes its images again. `SILLAGE_GL_SCREEN=file.png` writes, with a capture, what the window holds just before the swap (read back from it): the check that the copy to the screen is the right way up. When Vulkan fails (no loader, no driver, no device, an error while it starts), `Game.kt` prints one line with the reason and the package that would bring it (`Advice`), and opens OpenGL ES in the same window for the rest of the run; if that fails too, the game stops with both reasons and the packages to install. `--renderer vulkan` and `--validation` keep Vulkan alone.
- **Measured** (Intel Arc, Mesa 26.3, 1280 × 800, qa `rendu`): against the Vulkan reference pictures of the six island views, 0.0002 % to 0.0025 % of the pixels differ by more than 16 levels and the mean difference is 0.002 to 0.004 levels out of 255 (edges: the multisample positions and the resolve); debug lines differ more (0.34 % of the pixels), as the two APIs do not rasterise lines alike. The quality battery fails above 0.02 % and 0.05.

## Windows

`platform/WaylandWindow.kt` talks to `libwayland-client` through FFM. Requests use `wl_proxy_marshal_array_flags` (arguments in an array, no variadic calls). Every event arrives through one dispatcher installed with `wl_proxy_add_dispatcher`, routed by object and event name. The interface tables of the protocols outside the library (xdg-shell, xdg-decoration, relative pointer, pointer constraints, cursor shape) are written by hand, as `wayland-scanner` would generate them; `WaylandTablesTest` checks them. The buffer scale follows the compositor (sharp at 200 %). `XcbWindow.kt` is the X11 fallback through `libxcb`. Keys are Linux evdev codes, so they name physical positions on every layout.

`Win32Window.kt` is the window on Windows, through `user32`: a window class whose procedure is an upcall into Kotlin, messages drained with `PeekMessage` each frame. Keys arrive as scan codes, which are the same positions as evdev's for the main block (the extended ones — arrows, right Ctrl, the keypad's Enter — are translated by a small table), typed text as `WM_CHAR`, so layouts and dead keys are Windows' business. A captured mouse is hidden, clipped to the window and brought back to its centre after each move. The surface is `VK_KHR_win32_surface`. `SILLAGE_KEYS=1` prints each key as it arrives.

In a page the window is a canvas (`src@wasmJs/…/web/`: keys by `KeyboardEvent.code`, pointer lock, touches); on Android a `GLSurfaceView` in `GameActivity`, which builds the scene on a thread of its own so that the first frame never waits for it. Both hand fingers to `Touches`.

## Physics

See [PHYSICS.md](PHYSICS.md) for the user's view. Inside `PhysicsWorld`:

- **Data**: one slot per body in parallel arrays (position, rotation, shape, type, …) and a 20-float solver state per body (velocity, angular velocity, inverse mass, world inverse inertia, displacement and rotation during the step), contiguous so that an impulse touches one or two cache lines. A `Pose` per body (centre and axes as 12 floats) is updated in place when the body moved.
- **Step**: prepare bodies (poses, bounds widened by the distance travelled) → broad phase (uniform grid of the bodies that are not static, sorted `Long` keys; the static ones found in their box tree, their pairs put in the order the cells would give) → narrow phase (`Collide.kt`: one routine per pair of shapes, into a per-thread `ContactPoints`) → contact preparation (points matched with last step's by feature id and position for warm starting; friction patches) → substeps (integrate velocities, warm start, solve with bias, integrate positions, relax) → restitution → sleep (islands).
- **Threads**: `Workers.kt` is a pool of up to 8 threads per process. A job is cut into fixed chunks; each chunk writes only its own data, and results are merged in chunk order. Each job is published as an immutable task with its own counters, so a late worker can never take part in the next job. The solver colours the contact graph (at most 32 colours, the rest solved alone at the end) so that contacts of one colour share no moving body. Colouring starts only above a fixed size, so the order depends on the scene, never on the number of threads.
- **SIMD lanes** (`PhysicsWorld.Wide`, only with the `jdk.incubator.vector` module): each step lays the patches of each colour out in batches of one SIMD vector (8 lanes with AVX2), sorted by their number of points, their data as columns (24 floats per point slot, 24 per patch, the two bodies' 20 in the batch's own array), built once and read by the 12 passes of the substeps; the impulses go back to the contact sets at the end. Patches scaled for support stay scalar, after their colour's batches; the hidden loads are applied lane by lane in scalar code. Every lane mirrors `solvePatch` and `warmStartPatch` operation for operation (masks where they `continue`, the same comparisons for `max` and `coerceIn`), so `PhysicsTest.leSolveurVectorielDonneLeMemeResultat` compares the two solvers bit for bit, with and without threads and mass ratios. Three traps, each worth a factor: the species must be a `static final` constant (`WideLanes`), else nothing becomes SIMD (30 times slower); a method over 8,000 bytes of bytecode is never compiled by C2 (the passes are cut in several methods that hand the velocities over through the batch's array); and Kotlin's null checks on values from Java calls made every vector escape and be allocated, so the engine is built with `-Xno-call-assertions`, `-Xno-receiver-assertions`, `-Xno-param-assertions`. `--add-modules` must also reach the compiler (`-Xadd-modules` in `engine/module.yaml`); the class is made by name, so a JVM without the module never loads it.
- **Queries**: `QueryTrees` keeps two dynamic box trees (`BoxTree.kt`, after Box2D's: surface-area insertion, rotations, fat leaves), one for the static and kinematic bodies, one for the dynamic ones, brought up to date on demand for the bodies marked or moving only; the still tree is built again top down (median splits, nodes laid out branch by branch) after many insertions. Rays walk the trees nearest branch first and skip branches beyond the nearest hit; shape tests (`touching`) and sweeps take the bodies whose boxes they overlap, sorted by id. Results are the same as a body-by-body search, ties included (`QueryTreeTest`).
- **Continuous collision** (`Sweep.kt`): GJK distance between rounded cores (the shape shrunk, then given back as a radius), conservative advancement along the relative motion, the time of impact found per triangle and per static or kinematic body; the body put back before the first touch.
- **Joint trees** (`JointTrees.kt`): each step, the groups of joined bodies under a heavy load whose joints form a forest (no cones, no limits near, no loops) are picked; per substep their rigid rows (`Joint.directJacobian`) give K = J M⁻¹ Jᵀ in blocks, factored from the leaves in (no fill-in) with the bodies' inverse inertia stiffened by the loads they carry, and solved in the rigid, biased and relax passes after the iterative joints. The world keeps one `Body` handle per slot (`PhysicsWorld.handle`), handed to the filters and the results, rather than making one each time.
- **Joints** (`Joints.kt`): the passes every joint runs (`apply`, `push`, `solvePoint`, `solveLock`) are written on floats with the operations of the vector, quaternion and `Mat3` functions they chained, in the same order, and make only the impulse they return; checked to the bit against the earlier code on 600 steps of every kind of joint. The hinge's own rows still use vectors.

### Changing the physics

The order of floating-point operations is part of the result. In the narrow phase and the queries, formulas are written component by component in a fixed order. `CollideTest` keeps fingerprints of thousands of contacts and rays, and the physics tests check determinism with and without threads. A refactoring must leave the fingerprints alone. A change that is meant to alter results updates them, and its commit says so. The `qa` battery then checks the behaviour that matters: stacks hold, nothing sinks or tunnels, the character never ends inside the scenery.

## Sound

`audio/Mixer.kt` mixes up to 48 voices into stereo floats: volume, pitch (resampling), pan or a position in the world (distance attenuation, constant-power panning, a low-pass for distance and for sounds behind the head), gliding volumes, fades on stop, voice stealing, and a soft limiter. The game thread changes voices and the audio thread renders; they meet under a short lock at the start of each block, and rendering allocates nothing. A sound longer than ten seconds read from a file (`Sound.decode`, `load`) is a `SoundSource` (`SoundStream.kt`): the Ogg Vorbis packets (`VorbisSource`, about 1 MB per stereo minute instead of 21 MB of floats) or a WAV file's integer samples (`WavSource`). The file is read to its end once when it is loaded (`VorbisScan`: every packet decoded, so that damage is refused there; what each packet adds counted; the true start and end from the granules). `play` gives each voice a `SoundCursor` of its own, made on the game's thread (a Vorbis decoder of its own); the audio thread moves its window (8192 frames) with `cover` as the voice reads, decoding the next packets, all without allocating (the decoder's reader, vectors, windows and IMDCTs are made once). A jump (an offset, a loop going round) starts again from the packet holding the frame, decoding the audio packet before it first, which gives back the half block it overlaps: the samples are the same, bit for bit, as when the stream is read from its start, and so is the mixer's output (`StreamTest`). The first frame follows the last one in the window, for loops. `audio/Audio.kt` hands the mixer to the platform's output (`platformAudioOutput`): on Linux `Alsa.kt` writes 16-bit stereo blocks of 5 ms from a high-priority thread and recovers from underruns; on FreeBSD, or whenever the device asked for is a path under `/dev/`, `DeviceAudio.kt` writes the same blocks to an OSS device; on Windows `WaveOut.kt` keeps a few 10 ms blocks queued in `winmm` and refills each as soon as it has played; a page renders into Web Audio buffers scheduled a little ahead, Android writes to an `AudioTrack`. `audio/Synth.kt` synthesises every sound of the engine from seeded noise, filters and damped modes, so they come out the same every time; the scene pre-synthesises its common sounds in the background as soon as sound starts.

### The dev mode

`./sillage dev` starts `sillage.dev.DevKt` with the engine and the Kotlin library on the class path, and the game's own classes outside it, in a `URLClassLoader` of their own. The Kotlin compiler that the toolchain downloaded (`kotlin-compiler-embeddable`) is loaded in another class loader and called by reflection (`K2JVMCompiler.exec`): nothing in the engine depends on it at compile time, and it is warmed up by one compilation as soon as the game starts. A `WatchService` watches the game's sources and resources and the engine's sources; a burst of events (an editor writing a file in several steps) counts once after 150 ms of quiet. A change of code compiles into `build/dev/GAME/classes-N` and calls the game's `main` again in a new class loader, on a thread of its own; its call to `game()` finds the loop running (`DevLink.offer`) and hands its scene over instead of opening a window. At the end of a frame the loop builds that scene and installs it the way `goTo` does, after `DevLink.carryOver` moved the player, the camera and the hour across, each only if the new code built it the same way as the old (`DevLink.Initial`). A change of resources does the same with the current class loader (`Assets.roots` points at the game's resources folder). A change of the engine ends the loop with code 75, and the script builds and starts again. Exceptions from the game's code (building, updating) are caught only in dev mode: they freeze the picture and show in `DevOverlay`.

Heavy runs are best capped in memory (`systemd-run --user --scope -p MemoryMax=4G …` with `-Xmx2g`). Measure speed on fixed cores (`taskset`) and compare old and new code alternately: a laptop's speed drifts with its load and temperature.

## Adding things

- **A system**: on the desktop, a branch in `platform/Os.kt`, its package names in `platform/Advice.kt` (what to type when something is missing), a `Window` (`openWindow` in `platform/Window.kt` chooses it; it gives the Vulkan instance extensions it needs and makes the surface), an `AudioOutput` (`platformAudioOutput`), the fonts' folders in `UiFont.kt`; libc calls that the system lacks stay behind `by lazy`. Then a packaging path in the `./sillage` script, a row and a recipe in [PLATFORMS.md](PLATFORMS.md) — with what it was really tried on. A system without Vulkan implements `Gl` and the `expect` declarations of `Platform.kt` in a source set of its own, as the web and Android do.
- **A Vulkan function**: add its signature handle in `vk/Vulkan.kt` if the shape is new, the function, and any struct in `vk/Structs.kt` with its exact layout (check it against the registry).
- **A shape**: a `Shape` subclass with volume, inertia, bounding radius, principal axes and `scaled`; the convex hull (`Hull.kt`, narrow phase in `CollideHull.kt`: separating axes with the Gauss map, clipping) and the compound (`Compound.kt`, a part index in each contact's feature id) are the examples to follow; a rank and the routines against every other shape in `Collide.kt` (and against triangles); its bounds in `PhysicsWorld.prepareBody`; ray and sweep tests in `Queries.kt`; tests; then new fingerprints.
- **A scene builder**: a function in `Scene` that makes a `Node` (sharing its mesh when the parameters repeat), documented in KDoc, in the guide and in the reference, with a check in `qa/…/Api.kt`.
- **A sound**: a function in `Sounds`, built from `Synth` with a fixed seed, and listed in `--export-sounds`.
