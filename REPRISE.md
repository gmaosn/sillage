# Sillage — reprise

## Pour reprendre

Sillage est un moteur 3D en Kotlin pur, plus ergonomique et agréable que KorGE, en 3D par défaut, avec son propre moteur physique. Il doit être aussi rapide que la JVM le permet et prêt pour Valhalla.

Choix du propriétaire (18 novembre 2026) : API publique en anglais ; Linux d'abord (Wayland, X11 en secours, x86-64 et ARM64 du Pi), avec une couche fenêtre prête pour d'autres systèmes plus tard ; aucune dépendance tierce (seules les bibliothèques du système : libvulkan, libwayland-client, libasound, libc, appelées par FFM).

Dépôt public GitHub `gmaosn/sillage` (licence Apache 2.0, NOTICE), publié le 21 novembre à la demande du propriétaire ; pousser `main` seulement (`git push`), jamais la branche locale `avant-publication` (l'historique d'avant le nettoyage des détails personnels).

Construire uniquement avec `./kotlin` (Kotlin Toolchain 0.14.0), jamais Gradle. Le JDK 25 du système n'a pas de javac : la toolchain fournit le sien.

```sh
./sillage run demo                     # construit ce qui a changé (rien : moins d'une seconde), puis joue
./sillage dev demo                     # joue et recharge à chaque enregistrement (code, modèles, sons ; moteur → redémarrage)
./sillage run demo --headless --smoke --frames 180 --capture build/captures/smoke.png
./sillage test                         # tests du moteur (./kotlin test -m engine)
./sillage qa --rapide                  # contrôle qualité
./sillage new monjeu ; ./sillage package demo
./kotlin build                         # la toolchain reste dessous ; jamais Gradle
```

Essais du mode dev : `tools/essai_dev.sh` (sans fenêtre) et `FENETRE=1 tools/essai_dev.sh` (vraie fenêtre Wayland dans un KWin isolé, `tools/kwin_isole.sh`, configuration dans build/tmp, jamais ~/.config).

Le moteur est un moteur de jeu générique, pour d'autres que nous (demande du propriétaire, 18 novembre) : rien de propre à l'île dans `engine/`, API publique en anglais documentée. Documentation en anglais (19 novembre, « écris la documentation ») : `README.md` à la racine, `docs/TUTORIAL.md` (un premier jeu en huit étapes, « Star garden »), `docs/GUIDE.md` (tout ce que la scène offre, par thème), `docs/PHYSICS.md` (le moteur physique, seul ou sous une scène), `docs/REFERENCE.md` (toute l'API publique, par paquet), `docs/ARCHITECTURE.md` (comment le moteur est construit, pour qui le modifie). Les exemples ont été compilés et exécutés dans un module temporaire. L'inventaire de l'API publique se refait avec `-Xexplicit-api=warning` ajouté un instant aux `freeCompilerArgs` de `engine/module.yaml` ; les constantes Vulkan sont passées en `internal`. Un jeu = `game("Titre", args) { … }` qui remplit une `Scene`. Deux démos : `demo/` (l'île des Alizés, modèles GLB, en français) et `playground/` (formes seules, en anglais).

La toolchain 0.14 ne permet de fixer des options JVM que pour les tests (`settings.jvm.test.freeJvmArgs`, déjà réglé) ; pour `run`, il faut `--jvm-args`. Sans `--enable-native-access`, la JVM avertit à chaque appel FFM.

Tout jeu accepte (`--help` les liste) `--headless`, `--smoke`, `--frames N`, `--capture fichier.png`, `--look-at ex,ey,ez,cx,cy,cz` (caméra fixe pour les captures, les déplacements restent relatifs à la caméra de jeu), `--size LxH`, `--animation clip`, `--hour H` (heure du jour au départ, pour les scènes qui en ont une), `--export-textures dossier` (les textures toutes prêtes en PNG), `--validation` (les couches de validation Vulkan ne sont pas installées sur le portable). En `--smoke`, le contrôle de fin exige le saut de l'image 40 : une capture avant l'image 41 est écrite puis le contrôle échoue, c'est normal.

Régénérer les modèles : `python3 tools/create_assets.py` (sans bibliothèque tierce, 0,3 s).

Contrôle qualité (module `qa`, demandé par le propriétaire le 18 novembre) : `systemd-run --user --scope -p MemoryMax=4G ./kotlin run -m qa --jvm-args="--enable-native-access=ALL-UNNAMED -Xmx2g" -- [--rapide] [--seulement physique,collisions,personnage,rendu,chargeurs,api,endurance,performance] [--graine N] [--refaire-references]`. Mode rapide ~1 min, complet ~2 min. Rapport : `build/qa/rapport.md` (tableaux contrôle, mesure, seuil, état) ; code de sortie 1 s'il y a un échec. Références : `qa/reference/vue-*.png` (six vues de l'île, dont une de nuit à 21 h 30) et `qa/reference/performance.txt` (base de vitesse de ce portable ; plus de 50 % plus lent = échec) ; `--refaire-references` les réécrit. `QA_DETAIL=1` (passé par `systemd-run -E QA_DETAIL=1`) imprime les cas fautifs ; `SILLAGE_TEMPS=1` imprime les images les plus lentes d'une partie.

Son : la démo joue par la sortie « default » d'ALSA (PipeWire sur le portable) ; `--mute` coupe tout, `--audio-device NOM` choisit la sortie, la touche M coupe ou rend le son. Sans fenêtre (`--headless`), le son est mixé image par image et rien ne sort : `--record-audio fichier.wav` l'enregistre. `--export-sounds dossier` écrit tous les sons du moteur en WAV. Ne jamais jouer de son à voix haute pendant les essais (le propriétaire l'entend) : tests sur le périphérique `null` d'ALSA, enregistrements hors ligne, spectrogrammes ; la sortie « default » n'a été ouverte qu'avec du silence.

Trajets scriptés : `--route "x,z x,z j w p2 …"` (le joueur rejoint chaque point ; `j` saute, `w` bascule course/marche, `pN` attend N s ; un point non atteint en 6 s est abandonné et signalé), `--trace` (position, sol, clip toutes les 30 images, `--trace-every N`). La capture se fait aussi à la fin du trajet. Promenade de référence (île, ponton, barque, retour par un saut, caisse du bout du ponton), 12 s :

```sh
./kotlin run -m demo --jvm-args=--enable-native-access=ALL-UNNAMED -- --headless --frames 6000 --record-audio build/sons/promenade.wav --route "-1.5,1.6 -3,3.8 -4.2,4 -2.4,3.9 -2.4,1.1 j -1,5 w 1.5,5 w 3,4 4.2,5.4 4.2,7.8 2,8 -1.4,8.4 -1.6,9.3 -2.5,10.5 -4,10.7 -4,11.6 -4,9.9 -3.4,10.4 j -2.2,10.4 -1.4,10.6 -1.4,12.2 p3"
```

## Passe courte sur le moteur (22 novembre 2026), sans changer l'API

Demandée par le propriétaire avant de retravailler la démo ; trois lots proposés, tous acceptés.

- **Caisses poussables** : `dynamic()` prenait 400 kg/m³ et le personnage pousse à 400 N, donc la caisse d'un mètre du README, du tutoriel et de `./sillage new` (400 kg) ne bougeait pas. Densité par défaut 50 kg/m³ (une caisse de bois vide : 50 kg pour un mètre) ; `pushForce` inchangé (le réalisme de l'étape 4 reste). `SceneTest.laCaisseParDefautSePousse` (celle d'un mètre avance, celle de deux mètres non). Trouvé en chemin : l'éclaboussure attendait que le centre du corps passe sous l'eau, donc une caisse légère qui flotte haut n'éclaboussait jamais ; c'est le dessous du corps qui compte maintenant.
- **Particules triées** de la plus lointaine à la plus proche (`ParticleSystem.sort`, tri de Shell sans allocation, sauté quand tout est lumineux).
- **`particle.frag` réparé** : il ne compilait plus depuis les ombres en cascades (21 novembre) et son binaire lisait le bloc de l'image avec l'ancienne disposition, décalée de 48 octets : les fumées et poussières prenaient les lampes de trois cases plus loin. `sky.frag.spv` et `particle.vert.spv` étaient restés d'avant eux aussi (sans effet visible). Garde : `ShadersTest` recompile chaque shader avec glslc et compare au `.spv` embarqué.
- **Découpe alpha dans les ombres** : `shadow.frag` et un second pipeline d'ombre, pris seulement par les maillages découpés (`Mesh.cutOut`) ; avec le shader pour tous, la passe d'ombre coûtait +0,1 ms de GPU sur le tas de 3 000 caisses, avec deux pipelines rien (1,42 contre 1,44 ms). L'enseigne de la démo ne le montre pas (son dos est un panneau plein).
- **Ombres allumées et éteintes en jeu** : `lighting.shadows` change d'une image à l'autre ; une scène commencée sans ombres fait refaire le moteur de rendu (avec ses cartes) la première fois qu'on les allume.
- Contrôle qa « ombres : découpe alpha respectée, allumées et éteintes en cours de jeu » (plaque à moitié découpée fabriquée par le contrôle ; contre-épreuve faite : sans le `discard`, il échoue).
- **Bases de vitesse** remesurées à charge 3 à 5 (cœurs 4 à 11) : celles de la physique gardées, rendu et île refaites (`rendu.1280` 1,05 ms, `rendu.2560` 0,89, `rendu.caisses10000` 1,05, `ile.miseajour` 0,16 ms et 24 Kio : la hausse des allocations de l'île date de la passe du 21 novembre, l'ancien code mesuré en alternance donne la même).
- Non reproduit : les neuf avertissements du moteur à la construction d'un jeu (ici, le moteur compile sans avertissement).

Limite restante : au début d'une poussée sur un lourd posé sur un léger, sur un sol glissant, le tout glisse de quelques cm avant que le frottement monte (Gauss–Seidel, une passe par sous-pas ; existait avant). Balayage de sphère contre boîte exact (arêtes et coins arrondis). `PhysicsWorld.remove(corps)` : le corps sort du monde, ses voisins endormis se réveillent, sa place sert au corps suivant (`Body.isRemoved`, `liveBodyCount`). ## Limites actuelles

Écrasement (trouvé le 21 novembre par le robot du terrain de jeu, graines 1, 9, 13) : corrigé par le lot physique (c121c3e), un corps coincé entre un cinématique et du statique est poussé de côté ; le contrôle qa compte encore à part les images d'écrasement (0 aujourd'hui).

Maillages GLB triangulés, couleurs de matériau et COLOR_0, hiérarchies, TRS et animations de nœuds, textures de couleur (une seule par matériau, TEXCOORD_0, 1024 pixels au plus, transformées de texture ignorées), squelettes (déformés sur le processeur) ; interpolation CUBICSPLINE, cibles de morphose et extensions requises refusées explicitement. Les normales des pièces animées supposent une échelle uniforme. Articulations souples (une charge lourde sur un corps léger fait céder : voir plus haut) ; la collision continue balaie le noyau du corps, pas toute sa forme ; les requêtes passent par une grille uniforme (une sphère balayée de plus de 0,5 m de rayon parcourt encore tous les corps). Les fichiers son sont décodés en entier en mémoire (pas de lecture en flux) ; pas de MP3 ; l'auditeur est sur la tête du joueur suivi, tourné comme la caméra (`listener`, 21 novembre). Deux images en vol ; un seul fil pour le rendu. Les normales des GLB de Blender (attribut NORMAL) sont recalculées et lissées par défaut ; `model(…, normals = Normals.FROM_FILE)` garde celles du fichier (21 novembre). Les lampes ne font pas d'ombre ; 16 au plus sont dessinées. Les particules sont triées de loin en près, mais pas avec les autres objets transparents (l'eau). Les ombres portées couvrent trois carrés en cascade jusqu'à la brume (21 novembre) ; une falaise qui sort droit de l'eau n'a pas d'écume (le rivage est le sol bas). Une seule scène à la fois.

Outils : `tools/shaders.sh` (glslc) recompile les SPIR-V ; `tools/create_assets.py` produit les six GLB de la démo ; `tools/create_island.py` est une variante Blender jamais exécutée.
