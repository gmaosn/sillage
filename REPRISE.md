# Sillage — reprise

## Pour reprendre

Sillage est un moteur 3D en Kotlin pur, plus ergonomique et agréable que KorGE, en 3D par défaut, avec son propre moteur physique. Il doit être aussi rapide que la JVM le permet et prêt pour Valhalla.

Choix du propriétaire (18 novembre 2026) : API publique en anglais ; Linux d'abord (Wayland, X11 en secours, x86-64 et ARM64 du Pi), avec une couche fenêtre prête pour d'autres systèmes plus tard ; aucune dépendance tierce (seules les bibliothèques du système : libvulkan, libwayland-client, libasound, libc, appelées par FFM).

Construire uniquement avec `./kotlin` (Kotlin Toolchain 0.14.0), jamais Gradle. Le JDK 25 du système n'a pas de javac : la toolchain fournit le sien.

```sh
./kotlin build
./kotlin test
./kotlin run -m demo --jvm-args=--enable-native-access=ALL-UNNAMED -- --headless --smoke --frames 180 --capture build/captures/smoke.png
./kotlin run -m demo --jvm-args=--enable-native-access=ALL-UNNAMED
./kotlin run -m playground --jvm-args=--enable-native-access=ALL-UNNAMED
```

Le moteur est un moteur de jeu générique, pour d'autres que nous (demande du propriétaire, 18 novembre) : rien de propre à l'île dans `engine/`, API publique en anglais documentée. Documentation en anglais (19 novembre, « écris la documentation ») : `README.md` à la racine, `docs/TUTORIAL.md` (un premier jeu en huit étapes, « Star garden »), `docs/GUIDE.md` (tout ce que la scène offre, par thème), `docs/PHYSICS.md` (le moteur physique, seul ou sous une scène), `docs/REFERENCE.md` (toute l'API publique, par paquet), `docs/ARCHITECTURE.md` (comment le moteur est construit, pour qui le modifie). Les exemples ont été compilés et exécutés dans un module temporaire. L'inventaire de l'API publique se refait avec `-Xexplicit-api=warning` ajouté un instant aux `freeCompilerArgs` de `engine/module.yaml` ; les constantes Vulkan sont passées en `internal`. Un jeu = `game("Titre", args) { … }` qui remplit une `Scene`. Deux démos : `demo/` (l'île des Alizés, modèles GLB, en français) et `playground/` (formes seules, en anglais).

La toolchain 0.14 ne permet de fixer des options JVM que pour les tests (`settings.jvm.test.freeJvmArgs`, déjà réglé) ; pour `run`, il faut `--jvm-args`. Sans `--enable-native-access`, la JVM avertit à chaque appel FFM.

Tout jeu accepte (`--help` les liste) `--headless`, `--smoke`, `--frames N`, `--capture fichier.png`, `--look-at ex,ey,ez,cx,cy,cz` (caméra fixe pour les captures, les déplacements restent relatifs à la caméra de jeu), `--size LxH`, `--animation clip`, `--hour H` (heure du jour au départ, pour les scènes qui en ont une), `--export-textures dossier` (les textures toutes prêtes en PNG), `--validation` (les couches de validation Vulkan ne sont pas installées sur le portable). En `--smoke`, le contrôle de fin exige le saut de l'image 40 : une capture avant l'image 41 est écrite puis le contrôle échoue, c'est normal.

Régénérer les modèles : `python3 tools/create_assets.py` (sans bibliothèque tierce, 0,3 s).

Contrôle qualité (module `qa`, demandé par le propriétaire le 18 novembre) : `systemd-run --user --scope -p MemoryMax=4G ./kotlin run -m qa --jvm-args="--enable-native-access=ALL-UNNAMED -Xmx2g" -- [--rapide] [--seulement physique,collisions,personnage,rendu,chargeurs,api,endurance,performance] [--graine N] [--refaire-references]`. Mode rapide ~1 min, complet ~2 min. Rapport : `build/qa/rapport.md` (tableaux contrôle, mesure, seuil, état) ; code de sortie 1 s'il y a un échec. Références : `qa/reference/vue-*.png` (six vues de l'île, dont une de nuit à 21 h 30) et `qa/reference/performance.txt` (base de vitesse de ce portable ; plus de 50 % plus lent = échec) ; `--refaire-references` les réécrit. `QA_DETAIL=1` (passé par `systemd-run -E QA_DETAIL=1`) imprime les cas fautifs ; `SILLAGE_TEMPS=1` imprime les images les plus lentes d'une partie.

Son : la démo joue par la sortie « default » d'ALSA (PipeWire sur le portable) ; `--mute` coupe tout, `--audio-device NOM` choisit la sortie, la touche M coupe ou rend le son. Sans fenêtre (`--headless`), le son est mixé image par image et rien ne sort : `--record-audio fichier.wav` l'enregistre. `--export-sounds dossier` écrit tous les sons du moteur en WAV. Ne jamais jouer de son à voix haute pendant les essais (le propriétaire l'entend) : tests sur le périphérique `null` d'ALSA, enregistrements hors ligne, spectrogrammes ; la sortie « default » n'a été ouverte qu'avec du silence.

Trajets scriptés : `--route "x,z x,z j w p2 …"` (le joueur rejoint chaque point ; `j` saute, `w` bascule course/marche, `pN` attend N s ; un point non atteint en 6 s est abandonné et signalé), `--trace` (position, sol, clip toutes les 30 images, `--trace-every N`). La capture se fait aussi à la fin du trajet. Promenade de référence (île, ponton, barque, retour par un saut, caisse du bout du ponton), 12 s :

```sh
./kotlin run -m demo --jvm-args=--enable-native-access=ALL-UNNAMED -- --headless --frames 6000 --record-audio build/sons/promenade.wav --route "-1.5,1.6 -3,3.8 -4.2,4 -2.4,3.9 -2.4,1.1 j -1,5 w 1.5,5 w 3,4 4.2,5.4 4.2,7.8 2,8 -1.4,8.4 -1.6,9.3 -2.5,10.5 -4,10.7 -4,11.6 -4,9.9 -3.4,10.4 j -2.2,10.4 -1.4,10.6 -1.4,12.2 p3"
```

## Plan

0. Maths prêtes pour Valhalla et JSON maison, JOML et Gson retirés. **Fait.**
1. Vulkan appelé par FFM (java.lang.foreign) à la place de LWJGL. **Fait** : capture identique au pixel près à `tools/reference/demo-smoke-180.png`.
Détour demandé le 18 novembre (« animer le personnage, ajouter des détails au sprite et au décor ») : **fait**, voir État.

2. Fenêtre Wayland par FFM, souris capturée (pointer-constraints, relative-pointer), touches par position physique (ZQSD en AZERTY = WASD en QWERTY), secours X11 pour Xvfb ; GLFW retiré, zéro dépendance tierce. **Fait** (voir État).
3. Moteur physique : corps rigides (sphère, boîte, capsule, maillage statique GLB), phase large et phase fine, solveur par impulsions séquentielles avec démarrage à chaud, frottement, rebond, sommeil. Bancs de mesure : pyramide de caisses stable, 10 000 corps, déterminisme. **Fait** (voir État) ; 10 000 corps en temps réel reste pour l'étape 6.
4. Personnage, tirs de rayons et déclencheurs sur cette physique ; la démo de l'île portée dessus. **Fait** (voir État), plus de nouvelles animations du marin.
5. Son (accord du propriétaire le 18 novembre) : mixeur en Kotlin pur, sortie par ALSA appelée par FFM (PipeWire derrière), sons spatialisés ; sons synthétisés par le moteur (vagues, pas selon la surface, mouettes, jingle), sans fichiers embarqués sauf accord. **Fait** (voir État) ; reste l'écoute du propriétaire.
5 bis. Frottement au centre des contacts, rapports de masses, allocations, suppression de corps. **Fait** (voir État). Reste l'écoute des sons par le propriétaire.
6. API plus agréable que KorGE : un fichier, 3D sans réglage (caméra, lumière, ciel par défaut), physique en une ligne ; deuxième démo à caisses, tonneaux et ballon. Ajouté par le propriétaire : moteur générique pour d'autres, première personne au choix. **Fait** (voir État).
7. Passe de performance : mesure du temps réel par image (CPU, GPU), plusieurs images en vol, instancing, zéro allocation par image (JFR), cache AOT, en-têtes compacts, ZGC générationnel, API Vector, essai sur une build Valhalla. **Fait**, phase fine sans allocation comprise (19 novembre, « réécris les collisions »), sauf l'API Vector et l'essai Valhalla (propres au JDK et non à Kotlin : pas sans l'accord du propriétaire, qui a rappelé « pure kotlin »).

## État (18 novembre 2026)

Le prototype a été écrit le matin du 18 par Codex sans jamais compiler. Repris : build réparé (bug de précédence `i and 1 == 0` dans `Geometrie.boite`), puis étape 0.

Maths dans `engine/src/sillage/math` : `Vec3`, `Quat`, `Mat4` immuables, sans identité, marqués `@ValueCandidate` pour devenir des `value class` quand Kotlin aura les classes valeur à plusieurs champs sur Valhalla. Ne jamais les comparer avec `===` ni se synchroniser dessus. Les boucles chaudes garderont leurs données dans des tableaux primitifs.

JSON dans `engine/src/sillage/io/Json.kt` : strict (RFC 8259), profondeur bornée à 256, les nombres gardent leur texte pour que `toFloat()` arrondisse une seule fois.

38 tests verts à l'étape 1 (physique du personnage, géométrie, GLB, maths, JSON). Démo vérifiée hors écran sur l'Arc B390 ; le chemin fenêtré a été vérifié sous Xvfb avant l'étape 0 (llvmpipe, Xvfb n'a pas DRI3).

Étape 1 : `engine/src/sillage/vk/`. `Vulkan.kt` charge `libvulkan.so.1`, une poignée FFM `static final` par forme de signature (le JIT l'inline), l'adresse de la fonction passée en argument ; les fonctions de périphérique viennent de `vkGetDeviceProcAddr`. `Struct.kt` décrit les structures C (alignements, champs imbriqués « extent.width », tableaux « srcOffsets[1].x ») et fournit `NativeStack`, une pile native réutilisée (aucune allocation native par image). `Structs.kt` et `Constants.kt` : 71 structures et 127 constantes écrites d'après la référence Odin (`/usr/lib/odin/vendor/vulkan`, générée depuis vk.xml, absent du portable) ; un test de transition les a comparées à LWJGL par réflexion (539 décalages de champs, 127 valeurs, tout identique) avant d'être supprimé avec LWJGL Vulkan. Le rendu reçoit une `SurfaceSource` (extensions, surface, taille), implémentée par les fenêtres de l'étape 2.

Non vérifié à l'étape 1 : le rappel de validation (upcall FFM) est écrit mais les couches de validation ne sont pas installées (`vulkan-validation-layers`, à installer par le propriétaire s'il le veut) ; la présentation Wayland a ensuite été vérifiée sur le vrai bureau par le propriétaire (« très fluide »). Les appels `critical` (sans transition d'état du thread) pour les vkCmd* sont repoussés à l'étape 6 : ils sont incompatibles avec le rappel de validation.

Le passage de JOML aux maths maison change 2 pixels sur 576 000 (bord d'un rocher, arrondi de la caméra) ; la position finale du personnage est la même. La référence a été remplacée par la capture de l'étape 0.

Animation (détour du 18 novembre, après l'étape 1) : le chargeur GLB garde la hiérarchie des nœuds et lit les animations glTF TRS (LINEAR avec slerp, STEP) ; c'est ce que Blender exporte pour des objets en plusieurs pièces parentées. `engine/src/sillage/Animation.kt` : `Modele` (nœuds, racines, clips, version aplatie identique à l'ancien chargeur), `Partie` (une pièce dessinée avec matrice de l'objet × pose), `Animateur` (échantillonnage, boucle ou arrêt sur la dernière clé, fondu depuis la pose courante, pose en tableaux plats). `Monde.modele()` garde les pièces d'un GLB animé ; `objet.animer("clip")` joue un clip ; le héros choisit seul `idle`, `run` (vitesse de lecture selon sa vitesse réelle), `jump`, `fall` (après 0,12 s en l'air) et pivote en douceur. Les squelettes (skins) restent refusés.

Modèles (`tools/create_assets.py`, écrit les nœuds et les animations) : marin en 12 nœuds (marinière rayée, col, foulard, ceinture, visage, chapeau de paille à ruban, bras et jambes articulés aux coudes et genoux), clips idle 2,4 s, run 0,6 s, jump, fall ; `palmiers.glb` (troncs bagués, palmes retombantes, clip « vent »), `ciel.glb` (nuages qui tournent autour de l'île, trois mouettes qui battent des ailes, clip « vol » de 60 s), `port.glb` (voilier qui tangue avec drapeau, trois bouées, lampe tournante du phare, fumée de cheminée, clip « vie » de 12 s) ; `village.glb` gagne volets, croisillons, jardinières, cheminée, banc, tonneaux, caisses, chemin de pierres, fleurs, touffes d'herbe, buissons, galerie et garde-corps du phare, pieux, bittes et lanterne du ponton, galets, étoiles de mer, bois flotté, château de sable. Collisions ajoutées dans `demo/.../Main.kt` (`obstacleAuSol`). Référence `tools/reference/demo-smoke-180.png` refaite avec ce décor (reproductible au pixel près). 46 tests verts.

Le code hérité de Codex était en français (`Monde`, `Joueur`, `Physique`, `Objet`…) ; il a été remplacé par l'API anglaise à l'étape 6 (voir plus bas). Les paragraphes d'état qui suivent gardent les anciens noms de leur époque.

Étape 2 (fenêtre maison) : `engine/src/sillage/platform/`. `Window.kt` (interface, `Key` = codes evdev par position physique, `openWindow` : Wayland si WAYLAND_DISPLAY, sinon X11 ; `SILLAGE_PLATFORM=wayland|x11` force). `WaylandWindow.kt` : libwayland-client par FFM ; requêtes par `wl_proxy_marshal_array_flags` (arguments en tableau, pas de variadique), tous les événements par un seul rappel installé avec `wl_proxy_add_dispatcher`, aiguillés par objet et par nom d'événement ; numéros de requêtes relus par nom dans les tables `wl_interface` ; tables des protocoles hors bibliothèque écrites comme wayland-scanner (xdg-shell v5, xdg-decoration côté serveur, relative-pointer, pointer-constraints verrou persistant, cursor-shape) ; échelle de tampon par `preferred_buffer_scale` (net à 200 %) ; clic gauche ou Tab capture la souris. `XcbWindow.kt` : libxcb par FFM (décalages des événements vérifiés avec gcc), curseur invisible et retour au centre pour la capture. Vulkan crée la surface Wayland ou XCB (plus Xlib). `Native.kt` : poll, close, free de la libc. LWJGL est retiré : seule dépendance, la bibliothèque standard Kotlin.

Vérifié à l'étape 2 : hors écran 0 pixel d'écart avec la référence ; X11 sous Xvfb (llvmpipe), écran photographié ; Wayland dans un KWin virtuel isolé sur l'Arc à 60 i/s, décorations KWin, titre mis à jour, à l'échelle 2 rendu net (2 teintes dans le texte du HUD). Méthode KWin : `XDG_CONFIG_HOME/DATA/CACHE/STATE` dans le scratchpad, `dbus-run-session -- env -u DISPLAY -u WAYLAND_DISPLAY kwin_wayland --virtual --no-lockscreen --width 1280 --height 800 --socket sillage-test --exit-with-session script.sh`, capture par `spectacle -b -n -f -o fichier.png` dans le script ; pour l'échelle 2, mettre `"scale": 2` et le mode 2560×1600 dans le `kwinoutputconfig.json` isolé. Non vérifié sans le propriétaire : clavier, verrou du pointeur et mouvement relatif, molette, redimensionnement et bouton de fermeture sur le vrai bureau (on ne peut pas injecter d'entrées dans le KWin virtuel sans toucher au vrai).

Caméra (correction du 18 novembre, signalée par le propriétaire : « quand on rencontre un obstacle et qu'on continue à avancer, ça zoome très près ») : en glissant contre un palmier ou un coin de bâtiment, l'obstacle passait entre le héros et la caméra, qui se collait à 0,35 m de sa tête. Désormais `Boite.camera` (faux pour les objets fins : palmiers, tonneaux, caisses, buissons, banc, lanterne, château) : un objet fin ne rapproche pas la caméra, elle recule juste derrière s'il tomberait sur elle ; un bâtiment la rapproche toujours, mais elle pivote doucement vers la vue dégagée la plus proche quand le héros avance et que la souris est calme depuis 0,4 s ; le relief la lève au lieu de la rapprocher. Mesuré sur les mêmes trajets de glissade : ancienne caméra 1 275 images sous 2 m (minimum 0,35 m), nouvelle aucune (minimum 4,37 m) ; `CameraTest` le garde.

Étape 3 (moteur physique) : `engine/src/sillage/physics/`. `Shape.kt` (sphère, boîte, capsule, masse et inertie), `TriangleMesh.kt` (maillage statique à faces uniques, arbre de boîtes, arêtes « actives » : bord libre ou pli convexe de plus de 5°, les autres ne donnent ni axe ni normale, contre les collisions fantômes), `Collide.kt` (sphères et capsules analytiques ; capsule-boîte et capsule-triangle par découpage de face comme Box2D ; boîte-boîte et boîte-triangle par axes séparateurs puis découpage de face, 4 points au plus ; une normale par point), `PhysicsWorld.kt` (corps : état du solveur regroupé par corps, 20 flottants ; grille uniforme triée pour les paires, sans doublon ; solveur à impulsions séquentielles souples à 4 sous-pas d'après Box2D v3, démarrage à chaud par paire et par point, frottement, résistance au roulement des boules et capsules, rebond, contacts anticipés ; sommeil par îlots avec le critère de Box2D v3 ; corps cinématiques), `LongIntMap.kt`. API en anglais : `PhysicsWorld.add(shape, position, rotation, type, density | mass, friction, restitution)`, `Body` (position, rotation, velocity, applyImpulse, moveTo pour les cinématiques, isSleeping). 15 tests (`PhysicsTest`) dont pile, rebond, frottement, roulement, conservation, déterminisme, plaque mince.

Bancs (`./kotlin run -m bench --jvm-args="-Xmx2g --enable-native-access=ALL-UNNAMED" -- pyramid determinism pile 1000`, sous `systemd-run --user --scope -p MemoryMax=4G`) : pyramide de 210 caisses stable (glissement 3,6 mm ; enfoncement 27 mm en haut, souplesse des contacts qui s'additionne rangée par rangée) ; déterminisme au bit près sur 1000 corps ; tas éveillé : 1000 corps 6,2 ms, 3000 corps 24 ms, 10 000 corps 65 ms par pas (environ 6 µs par corps actif ; détail : solveur 50 %, paires 20 %, contacts 23 %). Pistes de l'étape 6 : paires persistantes avec boîtes élargies, contacts sans allocation, solveur vectoriel (API Vector), éventuellement plusieurs fils.

Démo : `Monde.corps` (PhysicsWorld) reçoit le terrain (maillage) et chaque obstacle (boîte statique) ; le héros y est une capsule cinématique qui suit le contrôleur de Codex et pousse les corps (téléportée si elle saute de plus d'un mètre, à la réapparition) ; `caisse()` et `ballon()` (modèles `caisse.glb`, `ballon.glb`) ; `Objet.orientation` pour les objets physiques. Une pile de trois caisses, une caisse seule et un ballon devant le départ, deux caisses sur la plage, une au bout du ponton. Le centre de l'île est bosselé (24 cm sous une caisse en (1,3 ; 0,5)) : une pile y basculait, elle est posée sur un endroit plat (vérifié). Référence de capture refaite. 69 tests verts.

Réalisme (18 novembre, demandé par le propriétaire) : `RealismeTest` compare le moteur aux formules (chute libre 0,1 %, glissement 0,4 % dans tous les sens, plan incliné exact, seuils d'adhérence et de basculement, boule qui roule 0,0 %, chocs élastiques exacts, rebonds 2 à 3 %, moment cinétique 1,5 % sur 5 s, rapports de masses). Corrigé : frottement anisotrope (première direction alignée sur la vitesse de glissement, impulsions reprises en vecteur du monde), effet gyroscopique implicite, contact sphère-triangle sur une couture (point sous le centre : un point décentré tournait avec la boule et la faisait sauter), ancrage des sphères sans rotation (la boule ne s'enfonce plus en roulant). Raideur des contacts 30 Hz ; au-delà d'un rapport de masses 1:10, `substeps = 8`.

Surfaces (demandé par le propriétaire : « une balle ralentirait plus vite dans de l'herbe que sur une route ») : `Material(friction, rollingResistance, bounce)` par triangle de `TriangleMesh` ; préréglages `ROAD`, `GRASS`, `SAND`, `WOOD`, `STONE`, `ICE` ; `Material.named` reconnaît les noms de matériaux Blender en anglais ou en français (herbe, sable, bois, pierre, route, glace…) ; `Monde.terrain(glb, surfaces)` les applique au terrain. Mesuré : boule lancée à 3 m/s, 42,8 m sur la route, 5,3 m dans l'herbe, 2,1 m dans le sable (théorie v²/(2·5/7·μr·g) à 0,3 % près) ; caisse sur la glace 3,4 m, sur l'herbe 0,7 m ; rebond amorti par l'herbe. Le ballon de la démo freine sur l'herbe, s'arrête vite dans le sable, roule plus loin sur le ponton.

Style graphique (18 novembre, demandé par le propriétaire : « des graphismes un peu naïfs mais néanmoins lissés et harmonieux, comme GameCube / Wii pour les Zelda » — un rendu toon original, pas une copie) : rendu à la taille réelle de la fenêtre (hors écran 1280×800) avec anticrénelage MSAA 4× (image multi-échantillonnée résolue, viewport et scissor dynamiques, cibles refaites au redimensionnement) ; normales lissées entre faces de moins de 55° (`Maillage.lisse`) ; shader toon adouci (`toon.frag` : terminateur et bande claire en `smoothstep`, ombres bleu-violet, ambiance ciel/sol, liseré réservé aux silhouettes, brume vers la couleur de l'horizon), constantes poussées : mvp, modèle en trois lignes, œil et temps ; dôme de ciel en dégradé avec halo du soleil (`Monde.ciel`, suit la caméra) ; ombres portées douces (`ombre.frag`, second pipeline à transparence sans écriture de profondeur, `Monde.ombre(objet, rayon)`, sous le héros, les caisses, le ballon). Modèles plus ronds (`rounded`, superellipsoïde dans `create_assets.py`) : marin arrondi aux grands yeux, marinière rayée par bandes, caisses biseautées, sphères, cônes et troncs plus fins, terrain à 12 anneaux et 96 côtés. Couleurs de l'interface données en sRGB (`Couleur.srgb`). Référence de capture refaite en 1280×800.

Étape 4 (personnage sur la physique) : `physics/Queries.kt` (`raycast` avec rayon optionnel contre sphères, boîtes, capsules et maillages par l'arbre de boîtes, `groundBelow`, `touching` : contacts d'une forme placée quelque part), `Body.tag` (étiquette libre), `physics/Character.kt` (personnage virtuel à la Jolt : sous-pas de 1/120 s, vitesse qui suit le plan du sol, sortie des pénétrations verticale sur sol praticable et glissement contre les murs, marches de 35 cm par haut-avant-bas, collage au sol en descente, poussée bornée à 400 N jusqu'à la vitesse voulue — une caisse de 140 kg sur μ = 0,6 ne bouge pas, une de 50 kg avance doucement, un ballon part à la vitesse du marin —, jeu de 5 mm contre les objets mobiles pour que la capsule cinématique ne les bouscule pas, poids appliqué à ce qu'on a sous les pieds). Le contrôleur de Codex (`Physique`, `Boite`) est retiré ; `Joueur` enveloppe le `Character` avec le tampon de saut et le temps de coyote ; caméra, ombres et placement passent par les rayons (`Physics.kt` : `libreRelief`, `libreObstacles`, `distanceCamera` ; l'étiquette `Mince` marque les objets fins). Zones (`physics/Trigger.kt`) : `addTrigger(forme, position)`, `onEnter`/`onExit` appelés après chaque pas, `filter` (par défaut tout ce qui bouge, personnages compris), `enabled` ; les coquillages de la démo sont ramassés par une zone (`MondeTest`). Touche Maj : marcher. Limites corrigées (18 novembre, demandé par le propriétaire : « corrige ces limites ») : le contrôle qualité passe entièrement (58 contrôles, 0 échec). Résultats (contrôle qualité, groupe performance, en alternance, cœurs 4 à 11, charge ~3) : aucune différence mesurable entre JDK 25, Valhalla tel quel et Valhalla avec les classes valeur (pile de 995 corps 3,6–4,1 ms ; île 0,14–0,16 ms ; image 1280×800 0,91–1,05 ms ; allocations de l'île 16,4 Kio (JDK 25) contre 17,9–20,8 Kio avec les classes valeur : pas de baisse). Avec les classes valeur, 40 contrôles sur 41 passent (vues au pixel près, déterminisme) ; seul « pas de fuite » dépasse de peu (+41,5 Mo pour 40) sur cette JVM d'essai. À refaire quand Kotlin écrira des classes valeur et des types non nuls pour la JVM.

## Limites actuelles

Maillages GLB triangulés, couleurs de matériau et COLOR_0, hiérarchies, TRS et animations de nœuds ; textures, squelettes, interpolation CUBICSPLINE et extensions requises refusés explicitement. Les normales des pièces animées supposent une échelle uniforme. Pas encore d'articulations ni de collision continue pour les projectiles (mesuré : une sphère de 10 cm ne traverse ni une dalle de 10 cm ni un sol maillé jusqu'à 320 m/s) ; les requêtes passent par une grille uniforme (une sphère balayée de plus de 0,5 m de rayon parcourt encore tous les corps). Le personnage ne suit pas le mouvement horizontal d'une plateforme (la barque ne fait que monter et descendre). Pas de son pour une chute dans l'eau ; le mixeur ne fait ni effet Doppler ni réverbération ; pas de lecture de sons compressés (OGG, MP3), seulement WAV. Deux images en vol ; un seul fil pour le rendu. Les normales des GLB de Blender (attribut NORMAL) sont ignorées : elles sont recalculées et lissées. Les lampes ne font pas d'ombre ; 16 au plus sont dessinées. Les particules ne sont pas triées (fumées qui se croisent : ordre de mélange approximatif). Les textures d'image des GLB restent refusées (seules les textures peintes par le moteur existent). Les ombres portées couvrent un carré de 48 m autour de ce que regarde la caméra (au-delà, rien) ; une falaise qui sort droit de l'eau n'a pas d'écume (le rivage est le sol bas). Activer ou couper les ombres portées demande une autre scène (tout le reste de l'éclairage change d'une image à l'autre). Une seule scène à la fois ; pas de menus ni de texte saisi ; une police bitmap unique.

Outils : `tools/shaders.sh` (glslc) recompile les SPIR-V ; `tools/create_assets.py` produit les six GLB de la démo ; `tools/create_island.py` est une variante Blender jamais exécutée.
